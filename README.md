# DentPilot Admin — لوحة التحكم الإدارية

لوحة تحكم احترافية لإدارة تفعيل وبيع تطبيقات **DentPilot Student** و **DentPilot Clinic**:
إدارة الوكلاء، توليد أكواد التفعيل، فرض الحدود اليومية، ومتابعة الأكواد والتفعيلات — بواجهة عربية RTL كاملة قابلة للتثبيت كتطبيق (PWA).

> **الأهم:** لوحة التحكم تستخدم **نفس خوارزمية التفعيل الأصلية** الموجودة داخل تطبيقاتك حرفياً (بدون أي تعديل). أي كود يُنشأ هنا يعمل مباشرة داخل التطبيقات الحالية دون تغيير عليها.

---

## ⚡ وضع التجربة (بلا تسجيل دخول) — مُفعَّل حالياً

هذه النسخة مضبوطة على **وضع التجربة**: تفتح مباشرة على لوحة التحكم بلا صفحة دخول
ولا اسم مستخدم ولا كلمة مرور، وتعمل بالكامل داخل المتصفّح (بلا خادم أو قاعدة بيانات)،
فتُنشر على Vercel وتعمل فوراً.

- التحكم بالوضع عبر ملف واحد: **`config.js`** → `DEMO_MODE: true`.
- بيانات التجربة تُحفظ محلياً في المتصفّح (localStorage) — لكل جهاز/متصفّح بياناته.
  لتصفيرها: افتح Console واكتب `DemoReset()`.
- توليد الأكواد وفحص الأجهزة يعملان بنفس الخوارزمية الأصلية، فالأكواد صالحة داخل التطبيقات.
- **لم يُحذف نظام الدخول.** كل ملفات المصادقة و `/api` باقية كما هي.

### إعادة تفعيل تسجيل الدخول والحماية لاحقاً
1. في `config.js` غيّر `DEMO_MODE` إلى `false`.
2. اضبط قاعدة البيانات ومتغيّرات البيئة (`SUPABASE_URL`, `SUPABASE_SERVICE_KEY`, `AUTH_SECRET`)
   كما في الأقسام أدناه، ثم أعِد النشر.

يعود النظام عندها إلى الوضع الكامل: شاشة إنشاء المالك مرّة واحدة، ثم تسجيل الدخول والصلاحيات.

## 1) نظرة سريعة على البنية

| الطبقة | التقنية | الملاحظة |
|---|---|---|
| الواجهة | HTML/CSS/JS نقي (RTL, PWA) | بلا خطوة بناء، تُقدَّم كملفات ثابتة |
| الخادم | دوال Vercel Serverless في `/api` | **بدون أي مكتبات خارجية** (crypto + fetch المدمجان) |
| قاعدة البيانات | Supabase (PostgreSQL) عبر REST | مع رجوع تلقائي لملف محلي أثناء التطوير |
| المصادقة | تجزئة كلمات المرور (scrypt) + رموز جلسة موقّعة (HMAC) | دورَان: `super_admin` و `agent` |

**نقطة مهمة عن الأمان:** سرّ التفعيل ومنطق الحدود يعملان على الخادم فقط؛ المتصفّح لا يرى مفتاح قاعدة البيانات ولا يستطيع تجاوز الحدود.

## 2) التشغيل محلياً (بدون أي إعداد)

يكفي وجود Node 18 فأحدث:

```bash
node server.js
# افتح http://localhost:3000
```

عند غياب إعدادات Supabase، تُحفظ البيانات تلقائياً في ملف محلي `.data/db.json`
(مناسب للتجربة؛ البيانات تبقى بعد إعادة التشغيل). أول فتحة تطلب إنشاء حساب المالك.

### تشغيل الاختبارات

```bash
node test/run-tests.js
```

يشغّل 20 اختباراً شاملاً على المنطق الحقيقي (انظر `TESTING.md`).

## 3) ربط قاعدة البيانات (Supabase) للإنتاج

1. أنشئ مشروعاً على <https://supabase.com>.
2. من **SQL Editor → New query**، الصق محتوى `db/schema.sql` بالكامل ثم **Run**.
   (يُنشئ جدولي `users` و `codes` ويُفعّل RLS لمنع الوصول عبر المفتاح العام.)
3. من **Project Settings → API** انسخ:
   - `Project URL` → المتغيّر `SUPABASE_URL`
   - مفتاح `service_role` (السرّي) → المتغيّر `SUPABASE_SERVICE_KEY`
   > مفتاح `service_role` سرّي ويُوضع في متغيّرات البيئة على الخادم فقط، ولا يُرسل للمتصفّح إطلاقاً.
4. ولّد سرّ توقيع الجلسات:
   ```bash
   node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
   ```
   وضعه في `AUTH_SECRET`.

راجع `.env.example` لكل المتغيّرات. بمجرّد ضبط `SUPABASE_URL` و `SUPABASE_SERVICE_KEY`
ينتقل النظام تلقائياً من الملف المحلي إلى Supabase.

## 4) النشر على GitHub ثم Vercel

### أ) الرفع إلى GitHub
```bash
git init
git add .
git commit -m "DentPilot Admin"
git branch -M main
git remote add origin https://github.com/<user>/dentpilot-admin.git
git push -u origin main
```

### ب) النشر على Vercel
1. <https://vercel.com> → **Add New → Project** واختر المستودع.
2. اترك إعدادات البناء كما هي (لا توجد خطوة بناء — المشروع ثابت + دوال).
3. في **Settings → Environment Variables** أضف:
   - `AUTH_SECRET`
   - `SUPABASE_URL`
   - `SUPABASE_SERVICE_KEY`
   - (اختياري) `DAY_RESET_OFFSET_MINUTES` = `180`
4. **Deploy**. بعد النشر افتح الرابط؛ أول زيارة تطلب إنشاء حساب المالك.

> Vercel يقدّم الملفات الثابتة من الجذر ويشغّل كل ملف في `/api` كدالة Serverless تلقائياً.

### ج) النشر على Netlify (نمط Netlify Functions)

المشروع مهيّأ للنشر على Netlify دون تغيير أي منطق أو قاعدة بيانات:

- الدوال في **`netlify/functions/`** تلفّ نفس معالجات `/api` عبر محوّل رفيع في `netlify/lib/adapter.js`.
- الإعداد في **`netlify.toml`**: ينشر الموقع الثابت، يسجّل مجلّد الدوال، ويعيد كتابة
  `‏/api/*` → `‏/.netlify/functions/:splat` — فتبقى نداءات الواجهة إلى `/api/...` كما هي
  (بلا تغيير في `api.js` أو `app.js` أو `agent-portal.js`). ورابط `‏/agent` يعمل عبر إعادة كتابة إلى `‏/agent.html`.

خطوات النشر:
1. ارفع المشروع إلى GitHub (كما في القسم أ).
2. في Netlify: **Add new site → Import an existing project** واختر المستودع (اترك أمر البناء فارغاً؛ الإعداد في `netlify.toml`).
3. **Site settings → Environment variables** أضِف: `AUTH_SECRET`، `SUPABASE_URL`، `SUPABASE_SERVICE_KEY`، و(اختياري) `DAY_RESET_OFFSET_MINUTES=180`.
4. **Deploy**. للتشخيص: `https://<site>.netlify.app/api/health`.

> نفس Supabase، نفس جدولي `users` و `codes`، نفس الصلاحيات والحدود — تغيّرت فقط طبقة التوجيه إلى Netlify Functions.

### د) النشر على GitHub Pages (داخل مجلد فرعي، وضع التجربة فقط)

المشروع مهيّأ للعمل من مسار فرعي مثل `https://<user>.github.io/dentpilot-admin/` دون شاشة سوداء:
كل مسارات الأصول المحلية في `index.html`, `agent.html`, `app.js`, `agent-portal.js`,
`manifest.webmanifest`, `service-worker.js` **نسبية** (`./...`)، وتُبنى روابط بوابة الوكيل ومولّد
الأكواد عبر دالة مركزية `siteBaseUrl()` (في `api.js`) تحسب المجلد الحالي تلقائياً — بلا أي اسم
مستودع مكتوب يدوياً في أي ملف.

خطوات النشر:
1. تأكّد أن `config.js` يحوي `DEMO_MODE: true` (**GitHub Pages استضافة ثابتة بلا خادم** —
   لا `‏/api` هناك إطلاقاً، فوضع التجربة هو الوحيد القابل للعمل على هذه المنصّة).
2. ادفع المشروع إلى مستودع، ثم **Settings → Pages** → المصدر: الفرع (وجذر المستودع `/`).
3. بعد النشر افتح `https://<user>.github.io/<repo>/` — تفتح اللوحة مباشرة (بلا تسجيل دخول، وضع التجربة).

> إن أردت النشر بالوضع الكامل (تسجيل دخول + Supabase) استخدم Vercel أو Netlify أعلاه؛
> GitHub Pages للاستعراض السريع لوضع التجربة فقط.

## 4.1) تشخيص مشاكل الدخول في الإنتاج (مهم)

على Vercel، نظام الملفات **للقراءة فقط ومؤقّت** — لذلك **قاعدة بيانات Supabase إلزامية في الإنتاج**.
بدونها لا تُحفظ الحسابات: تُنشئ المالك في طلب، ثم يفشل الدخول في الطلب التالي لأن البيانات لم تُحفظ.

**أولاً افتح نقطة التشخيص:** `https://<your-app>.vercel.app/api/health`

| ما تراه | المعنى | الحل |
|---|---|---|
| `backend: "unconfigured"` (503) | لم تُضبط متغيّرات Supabase | أضِف `SUPABASE_URL` و `SUPABASE_SERVICE_KEY` ثم أعِد النشر |
| `db: "unreachable"` + «الجداول غير موجودة» | لم يُشغَّل المخطّط | شغّل `db/schema.sql` في Supabase → SQL Editor |
| `db: "read_only"` عبر `/api/health?deep=1` | تستخدم مفتاح **anon** لا **service_role** | ضع مفتاح `service_role` السرّي في `SUPABASE_SERVICE_KEY` |
| `status: "ok"`, `db: "reachable"` | كل شيء سليم | الدخول يعمل |

للتأكّد الكامل بما فيه الكتابة: `https://<your-app>.vercel.app/api/health?deep=1`

**قائمة تحقّق سريعة للإنتاج:**
1. `db/schema.sql` شُغِّل في Supabase.
2. `SUPABASE_URL` = رابط المشروع (Project URL).
3. `SUPABASE_SERVICE_KEY` = مفتاح **service_role** (وليس anon).
4. `AUTH_SECRET` مضبوط.
5. أعِد النشر بعد أي تعديل على المتغيّرات (Vercel لا يطبّقها إلا بإعادة نشر).

> لا يوجد حساب افتراضي إطلاقاً. أول زيارة (بعد ضبط قاعدة البيانات) تعرض شاشة إنشاء المالك،
> والبيانات التي تدخلها هي اسم المستخدم وكلمة المرور.

## 👤 بوابة الوكيل (Agent Portal) — الدخول عبر رابط دعوة دائم

صفحة مستقلة وبسيطة للوكلاء فقط لإنشاء أكواد التفعيل — منفصلة عن لوحة الإدارة،
**بلا شاشة تسجيل دخول ولا اسم مستخدم/كلمة مرور**. الدخول يتم عبر رابط دعوة دائم من الإدارة:

```
/agent?key=AGT_xxxxxxxxxxxxxxxx
```

- **الملفات:** `agent.html` + `agent-portal.js` (بنفس التصميم؛ حُذفت شاشة الدخول فقط).
- عند فتح الرابط: تُفتح البوابة مباشرة، ويُعرَّف الوكيل تلقائياً من الرمز، ويُزال الرمز من شريط
  العنوان الظاهر (يبقى محفوظاً على الجهاز)، فيرى الوكيل حدّه وأكواده فقط.
- **نفس النظام تماماً:** تستدعي `‏/api/session` و `‏/api/codes` (لم تعد تستخدم `‏/api/login`).
  لا قاعدة بيانات جديدة ولا منطق توليد جديد — التوليد على الخادم ويُحفظ في **نفس جدول `codes`**.

**تحقّق الخادم (كما هو مطلوب):** لكل طلب من البوابة يتأكّد الخادم أن الرمز موجود، وأن الوكيل نشِط،
وأن الحد اليومي محترَم — قبل توليد أي كود. رمز الوكيل (`AGT_`) لا يفتح أي وظيفة إدارية إطلاقاً.

ما يحدث عند إنشاء كود من البوابة:
- يُحفظ في نفس جدول `codes` بمعرّف الوكيل (`agent_id`) واسمه.
- يظهر مباشرة في لوحة الإدارة (قسم الأكواد + لوحة المعلومات).
- يخضع لنفس الحد اليومي والصلاحيات (يُفرض من الخادم).
- الوكيل يرى أكواده فقط، ولا يرى أي بيانات أو إعدادات إدارية.

### التحكّم من لوحة الإدارة
- **إنشاء وكيل:** يُولَّد له رابط دعوة دائم تلقائياً.
- **نسخ رابط الدخول:** زر «نسخ رابط الدخول» بجانب كل وكيل (أو من نافذة التعديل).
- **توليد رابط جديد:** من نافذة تعديل الوكيل — يُبطل الرابط القديم فوراً (إن تسرّب).
- **إيقاف/تفعيل الوكيل:** الإيقاف يُبطل رابطه فوراً.
- **تحديد الحد اليومي**، و**مشاهدة أكواد كل وكيل** (قسم الأكواد يدعم البحث باسم الوكيل).

> نظام اسم المستخدم/كلمة المرور للوكيل **لم يُحذف** من القاعدة أو الخادم — فقط لم تعد بوابة
> الوكيل تستخدمه. يبقى دخول المالك بكلمة المرور كما هو دون أي تغيير.

> **مهم:** البوابة تستخدم الخادم الحقيقي وقاعدة البيانات (وضع الإدارة الكامل، وليس وضع التجربة).
> على Vercel/Netlify اضبط Supabase و `AUTH_SECRET`، واجعل `DEMO_MODE = false` في `config.js`
> حتى تشترك البوابة والإدارة في نفس البيانات. محلياً يعملان معاً عبر `node server.js`.

### ترقية قاعدة البيانات
أُضيف عمود `agent_token` إلى جدول `users`. أعِد تشغيل `db/schema.sql` في Supabase (آمن وغير مُتلِف —
يضيف العمود فقط إن كان ناقصاً). للوكلاء القدامى بلا رابط: اضغط «توليد رابط» في قائمة الوكلاء.

> **إذا ظهر `/agent?key=undefined`:** يعني أن الوكيل لا يملك رمزاً بعد — غالباً لأن عمود `agent_token`
> غير موجود في Supabase (لم تُشغّل الترقية) أو أن الوكيل أُنشئ قبلها. الحل:
> (1) شغّل `db/schema.sql` في Supabase، ثم (2) افتح قسم الوكلاء في اللوحة — النظام يولّد رمزاً
> تلقائياً لأي وكيل قديم بلا رمز (إصلاح ذاتي عند العرض). لن تبني اللوحة رابطاً يحتوي على «undefined» أبداً؛
> فإن تعذّر التوليد تظهر رسالة واضحة تطلب تشغيل الترقية.

### حسابات الوكلاء
ينشئها المالك من لوحة الإدارة (قسم الوكلاء ← إضافة وكيل)، ثم ينسخ **رابط الدخول** ويرسله للوكيل
عبر قناة آمنة. لا حاجة لإعطائه اسم مستخدم أو كلمة مرور.

## 🛟 الدعم والتفعيل + الخطط + سجل الإدارة (توسعة)

قسم جديد في اللوحة يدير كل عمليات التفعيل من مكان واحد، **إضافةً فوق النظام الحالي دون كسره**.

### ما يعمل اليوم بلا أي تحديث للتطبيق
- **الخطط الديناميكية** (قسم «الخطط»): إنشاء/تعديل/إيقاف خطط (اسم، عدد أيام، حالة). تظهر تلقائياً
  في مولّد الأكواد والتفعيل المباشر. «عدد الأيام» فارغ = مدى الحياة.
- **مولّد الأكواد** صار يعرض الخطط من قاعدة البيانات بدل «مدى الحياة فقط». التوليد القديم يبقى متوافقاً.
- **تفعيل مباشر** (قسم «الدعم والتفعيل»): إدخال Device ID + خطة → يُنشئ **سجل تفعيل حقيقي**
  في جدول `device_activations` **ويُصدر نفس الكود المربوط بالجهاز** (تسلّمه للعميل فيعمل في التطبيق الحالي كالمعتاد).
- **البحث** بالـ Device ID أو كود التفعيل، مع عرض: التطبيق، الحالة (تجربة/مفعّل/منتهٍ/موقوف)،
  الخطة، تاريخ البداية والانتهاء.
- **إجراءات**: تمديد، تغيير خطة، إيقاف، إعادة تفعيل — كسجلّات مرجعية في اللوحة.
- **سجل عمليات الإدارة** (تدقيق): من فعّل/مدّد/غيّر/أوقف، ومتى، وبأي خطة.

### قاعدة البيانات (ترقية آمنة)
أعِد تشغيل `db/schema.sql` في Supabase — يضيف جداول `plans` و `device_activations` و `admin_log`
وخططاً افتراضية، **دون المساس بجدولي `users` و `codes`**. (محلياً تُزرع الخطط تلقائياً.)

### ⚠️ ما يتطلّب تحديث التطبيق (لم يُنفّذ — إبلاغ فقط)
التطبيقات الحالية تتحقّق من التفعيل **محلياً بالكامل (بلا خادم)** — تأكّدنا بفحص `activation.js`.
لذلك «فتح التطبيق مفعّلاً بلا إدخال كود» أو «فرض الانتهاء/الإيقاف داخل التطبيق» **يتطلّب تحديثاً
بسيطاً لمرّة واحدة**. النقطة العامة `‏/api/device-status` جاهزة لذلك. المقتطف المطلوب إضافته للتطبيق مستقبلاً:

```js
// (اختياري، تحديث مستقبلي للتطبيق) — تفعيل تلقائي من الخادم دون إدخال كود
try {
  var id = DPActivation.getDeviceId();
  var r = await fetch('https://<your-site>/api/device-status?device=' + encodeURIComponent(id) + '&app=student');
  var j = await r.json();
  if (j.activated && j.code) DPActivation.activate(j.code); // يخزّن الكود محلياً كالمعتاد
} catch (e) { /* بلا إنترنت: يبقى التحقّق المحلي الحالي كما هو */ }
```

> ملاحظة: الحالات «منتهٍ/موقوف» تُدار في اللوحة الآن كمصدر حقيقة لفريق الدعم، وتصبح ملزِمة داخل
> التطبيق فقط بعد هذا التحديث. الكود المُعاد مشتقّ من الجهاز أصلاً (غير سرّي).

## 🎫 صفحة مولّد أكواد الوكيل — عامة ومباشرة (agent-generator.html)

صفحة بسيطة **عامة تماماً بلا مفتاح ولا توكن ولا أي حماية**. تُفتح مباشرة:

```
https://<site>/agent-generator.html
```

- يدخل الوكيل Device ID → يضغط توليد → يُنشأ الكود على **نفس الخادم بنفس الخوارزمية** ويُحفظ في **نفس جدول `codes`** (بـ `agent_id = null`) فيظهر فوراً في لوحة التحكم.
- **لا تسجيل دخول، لا اسم مستخدم، لا كلمة مرور، لا `?key=`، لا `agent_token`.**
- **بلا أي تعديل على Supabase أو `schema.sql` أو جدول `codes` أو خوارزمية التفعيل أو منطق إنشاء الأكواد.**

### التحكّم بالاستخدام (بلا قاعدة بيانات — متغيّرات بيئة على Netlify)
بما أنك منعت أي تعديل على قاعدة البيانات، فالمكان الوحيد لحفظ إعداد قابل للتغيير هو متغيّرات البيئة:

- `AGENT_PAGE_ENABLED` = `false` **لإيقاف الخدمة** مؤقتاً (الافتراضي: مفعّلة). عند الإيقاف تُرجِع الصفحة رسالة «الخدمة موقوفة».
- `AGENT_PAGE_DAILY_LIMIT` = عدد **الحد اليومي الإجمالي** للأكواد من هذه الصفحة (الافتراضي `0` = بلا حد). يُحسب «المُستخدم اليوم» من نفس جدول `codes` (قراءة فقط)، وعند بلوغ الحد تُرفض المحاولات حتى اليوم التالي.

تغييرهما من Netlify → Site settings → Environment variables (يسري فوراً بعد إعادة النشر). قسم «الوكلاء»
في اللوحة يعرض **حالة الخدمة والحد اليومي والمُستخدم اليوم** والرابط العام مع زر نسخ.

> ملاحظة صريحة: زرّ تشغيل/إيقاف **يُحفظ من داخل اللوحة** يحتاج مكان تخزين دائماً — وهو Supabase الذي منعتَ تعديله.
> لذلك التحكّم الحالي عبر متغيّرَي البيئة أعلاه (بلا قاعدة بيانات). إن رغبت لاحقاً بزرّ داخل اللوحة أخبرني (يتطلّب إضافة بسيطة على Supabase).

## 5) خريطة الملفات المهمة

- `agent.html` + `agent-portal.js` ← بوابة الوكيل (تعيد استخدام `api.js` و `/api`).

```
api/
  _lib/license.js   ← خوارزميتا Student/Clinic (منسوختان حرفياً من تطبيقاتك)
  _lib/auth.js      ← تجزئة كلمات المرور ورموز الجلسة
  _lib/db.js        ← طبقة البيانات (Supabase أو ملف محلي)
  _lib/guard.js     ← حراسة الصلاحيات (super_admin / agent)
  bootstrap.js      ← حالة الإعداد + إنشاء المالك مرّة واحدة
  login.js session.js
  agents.js         ← إدارة الوكلاء (CRUD)
  codes.js          ← فحص الجهاز + توليد الكود + الحدود + سجلّ الأكواد
  activations.js stats.js
db/schema.sql       ← مخطّط قاعدة البيانات
index.html app.js api.js styles.css   ← الواجهة
manifest.webmanifest service-worker.js ← إعداد PWA
server.js           ← خادم تطوير/اختبار محلي
test/run-tests.js   ← الاختبارات
```

## 6) كيف يعمل التفعيل (ملخّص تقني)

- كود التفعيل **دالة حتمية من معرّف الجهاز فقط** (ومن `PRODUCT_ID` في حالة Student).
- **لا يحتوي الكود على مدة اشتراك أو تاريخ انتهاء** — التفعيل دائم ومربوط بالجهاز.
  لذلك تُعرض «مدة الاشتراك» كـ *دائم (مدى الحياة)* فقط، مطابقةً لما تدعمه التطبيقات فعلياً.
- التطبيق يخزّن الكود محلياً ويتحقّق منه دون إنترنت.
  **نتيجة مهمة:** «إلغاء» كود من اللوحة هو إجراء تنظيمي في سجلّك فقط، ولا يُعطّل جهازاً
  سبق تفعيله، لأن التطبيقات لا تتصل بالخادم للتحقّق. (يمكن إضافة تحقّق أونلاين مستقبلاً إذا رغبت.)

## 7) الصلاحيات

- **Super Admin (المالك):** يُنشأ مرّة واحدة. يدير الوكلاء وحدودهم، ويرى كل الأكواد والتفعيلات والإحصاءات، ويستطيع توليد الأكواد.
- **Agent (الوكيل):** يُنشئه المالك فقط. يرى لوحته الخاصة فقط (بياناته، الحد، المتبقّي) ويولّد الأكواد ضمن حدّه اليومي. لا يصل لأي صفحة إدارية أخرى.

---

## 8) التجهيز للمستقبل (بلا كسر التوافق)

البنية مهيّأة لإضافة لاحقاً دون المساس بالتطبيقات الحالية:
تعديل بيانات صفحة التفعيل، أرقام الدعم، الأسعار، إدارة الاشتراكات، وإدارة الإصدارات —
يمكن إضافتها كجداول/نقاط API جديدة وأقسام في القائمة الجانبية.
